# 脱敏复盘：可以带走的方法

整理日期：2026-11-02（Asia/Taipei），v0.4.0。依据已有本地操作记录、回执和合成测试整理，不重新扫描现场。客户名称、目录清单、连接信息和密钥留在私有位置。

## 已有证据怎样解释

本次保全仍存活的加密进程相关证据，取得适用会话材料，先复制恢复若干目录，后在支持 FICLONE 的 Btrfs 上转为克隆原位恢复。图片完整解码、归档 CRC、PDF 解析渲染、音视频解码等只证明覆盖的结构检查通过。没有可信历史原件 hash 时，不能宣称与历史原件逐字节一致。

原位试验共 885 个文件与此前恢复的明文 SHA 一致，源文件身份/元数据未变；这仍不是 885 个历史原件比对。19:18:30 的日志有 52,708 个已提交文件、475.12 GB，errors/conflicts 各 0，另有 17 个文件头未判定项保留密文。随后 002b 回执于 19:25:06 采集到已确认 55,994 文件、527.09 GB，405 个历史文件头误判均已解决，当前未解决项为 0；仍有尾批待确认。恢复尚未结束，不以零错误推导全量成功。采样时间、可复算速度与边界见 [IN-PLACE.md](IN-PLACE.md) 和 [脱敏汇总](evidence/v0.3.0-field-summary.json)。

## 最有价值的操作经验

1. **先保全会随重启消失的证据。** 尚未提取适用材料时，升级和重装必须给易失证据留出机会。未重启也不保证 key 仍在。
2. **密钥提取并备份后，重新选择路线。** 已验证的 key 有独立备份，就不必再让冻结进程决定后续方案。是否保留进程、何时重建，应由证据需求和恢复目标决定，不能把早期保护手段变成永久约束。
3. **交付完整目录。** 旧交付只包含解密出来的文件，遗漏原本没有加密的原件。对业务来说这仍是缺目录。以后来源清单、交付核对与只读访问必须覆盖两类文件；原位恢复完成也要列出未判定、失败及排除项。
4. **尽早确认原厂还是非官方兼容设备。** 这决定能否走官方重装、升级和技术支持。先确认硬件身份，不把旧文档或推测当事实。
5. **多个 agent 共用机器时，按资源协调。** 按任务分工并不隔离 I/O：两个卷的全局 sync、扫描、hash、传输和监控会互相干扰。由一个执行编排者确认活动任务、资源预算和停续顺序；同类恢复长任务不重复启动。并行不是默认提速。
6. **状态写进可复用入口。** 记录任务、暂停原因、设备身份、日志位置和接续条件。历史命令不是再次执行的指令，SSH 或观察器退出不等于业务进程退出。
7. **让恢复优先于求全调查。** 复用已有清单，急需目录先恢复，范围扫描让出 I/O。清点完成不证明内容恢复完成。
8. **核对设备身份而非路径名。** USB 挂载路径可对应另一块盘，文件系统、容量、设备身份需要核对。独立容量池不等于独立故障域。
9. **预览错误追到文件。** 某图片预览失败但读回摘要一致、完整解码成功，只证明该文件通过所做检查，不能反推其他预览错误无害。

## 性能的根本问题：整份复制搬运了未加密字节

已知布局的大文件常见 `0x25`/参数 10，只有三段、约 12% 字节加密；`0x26` 只处理开头 1 MiB。旧方式却整份读、整份写，再整份逻辑读回算 SHA，没有加密的字节也反复搬运。因此，早期不同采样速度或日志落盘调用次数都不能解释根本成本，优化日志也不能消除整份复制。

FICLONE 克隆后只改加密段，再截 footer、归档后不覆盖地安装原名并删除密文，减少了这部分搬运与空间需求。源工具短时实验 8 线程批量同步为 244 MB/s；流水线初次切换前后各 600 秒，两文件系统合计约 113.45 → 178.13 MB/s、14.23 → 27.44 文件/s；较晚生产日志窗口合计约 327.48 MB/s。每个数字有不同文件分布与窗口，不是相同负载的严格对照。

流水线进一步取消每 64 文件等待整组结束的屏障，扫描、解密准备和提交并行，用有界队列限制在途工作；以 `syncfs` 代替影响整机的 `sync`，下一批屏障确认上一批安装，边界单独排空。原位脚本没有逐文件全量 SHA 读回；抽样 SHA、文件头规则与全量历史原件认证应分开表述。

完整逻辑读回可能命中页缓存，不能据此声称物理盘被完整读取第二遍。线程阶段累计时间不能相加冒充墙钟时间。CoW、快照引用、元数据和随机 I/O 仍可能限制速度，更多线程未必更快。

## 格式与密码学易错点

文件 key 记录在 588 字节 footer 开头 48 字节，不是文件最后 48 字节。ChaCha8 不等于 ChaCha20；跨段 counter 和调用边界不能按偏移重写。CBC 的 IV 错误可能只影响首个明文块，nonce 重复仍可能通过；marker、nonce 和文件头都只能提供部分证据。

扩展名不等于内容：PNG 可能名为 jpg，Office 可能是 OLE 容器，旧 MOV 可能没有 ftyp，AppleDouble/AppleSingle 元数据和 Office owner 文件也有不同结构。能识别的其他格式可以记录通过文件头检查，但不能冒充完整结构验证；确实认不出的表内扩展名仍保留密文。未知扩展名未经文件头判定不等于验证成功。

## 本次没有证明的事

- 所有目录、文件、会话或勒索变种均可恢复。
- 原 NAS 已清洁，或不存在数据外传。
- 新公开导出版本已经部署到 NAS，或合成模拟证明真实 FICLONE/掉电持久性。
- 某个吞吐或线程数对其他设备普遍成立。
- footer 归档能替代全文件备份，或能撤回业务后续编辑。
- 复制管线发布资格检查能直接认证原位目录，或代表网站、账号权限和 HTTPS 已上线。

这些未知项仍需按实际任务补充证据；已有验证不因换 agent 重复进行。


## 公开更正：克隆仍会累计增占

“原位恢复净增约等于零”的早期判断已撤回。Btrfs bookend extent 仍被部分引用就不会释放，局部改写可留下接近改写量的旧空间，已有负载约占完整文件的 9–12%。容量按 Btrfs 最小可用量、并发在途分配及预留计算；低空间整份写，不能用 df/statvfs 和逻辑删量保证净余量。详见 [自适应写](IN-PLACE.md)。

## 公开更正：目录名前缀不是系统目录证明

按 @/# 一刀切曾遗漏用户历史目录及回收站，旧示例也把错误带入公开版。现在默认只排明确系统 basename，工具目录逐一配置；用户自建 @/# 目录与 `#recycle` 纳入恢复。已结束的扫描须对旧规则遗漏的范围补恢复并单列结果，不以旧统计作为完整分母。

## 性能要区分 CPU、扫描、元数据和交付

C 后端把解密调用降到毫秒级后，4 线程扫描、有界队列与 1–24 THREADS 热调让恢复更接近磁盘上限；高吞吐窗口不是长期保证。根边界 SQLite 全表汇总曾停顿约 23 分钟，改用 completed 日志重放的内存累计。RAID5 元数据拥塞可让 clone 达秒级；先看成员盘和事务，不靠无限加线程。大批 unlink 会增加压力，不能把相关性说成唯一根因。

管理短命令的历史约 39 秒与恢复管理连接有关，优先级调优前后实际为 1.066→0.195 秒，不能全部归因于 nice/ionice。所有吞吐注明逻辑/物理口径、日志来源与采集时间；限速不是实测速率。

## 持续恢复与完整交付

不要为了测试、测速或等待把生产控制器停着。测试用独立目录与合成 key，必要切换只做短暂停稳并立即续跑。跨卷搬运要完整读写和完整读回后删源，先隔离来源并规划整个共享最终位置；源逻辑删量不是即时净释放。收尾核查和例外副本保留未知、冲突及缺项，不能把 root-done 当成全部恢复。

只读 SFTP 加 Web 可以零业务副本交付完整目录，恢复文件自动出现；过滤密文/临时文件，限制来源、权限和总下载速率，内外网分开验收。Mode 2 可保留数据卷，但先核对存储/加密层；只在 Configuration lost 路径继续，Not Installed 或初始化/删除提示就停。方法与边界见 [收尾和交付](RECOVERY-FINISHING.md)、[重建说明](REBUILD.md)。
